# Blueberry

An AI browser built with Electron, React and TypeScript. [DESIGN.md](./DESIGN.md) is the source of truth for all UI, so read it before changing anything visible. [ROADMAP.md](./ROADMAP.md) has the plan and how we build it, so read it before starting a feature.

## Commands

| Command | What it does |
|---|---|
| `pnpm install` | Install dependencies |
| `pnpm dev` | Run the app with hot reload |
| `pnpm run typecheck` | Typecheck main, preload, tests and renderers |
| `pnpm run lint` | Lint. Warnings are allowed, errors fail CI |
| `pnpm run test` | Run unit tests in `src/` with Vitest |
| `pnpm exec electron-vite build` | Build into `out/` |
| `pnpm run test:e2e` | Run Playwright against `out/`, so build first |
| `pnpm exec electron-builder --dir` | Package an unsigned app into `dist/` |
| `pnpm run eval` | Run Berry on real websites with the real model, which costs money. See `evals/README.md` |
| `pnpm run site:build` | Regenerate what comes from the app: in `site/`, the drawings, permission wording and checks on a row, and `src/main/pageActorArt.ts`, the bird drawn on pages. Run it after changing any of them |
| `pnpm run verify` | Typecheck, lint, unit tests, build and end-to-end tests, the same as CI on macOS |

CI runs typecheck, lint, unit tests and build on macOS and Windows. The end-to-end tests run on macOS for every PR, and on Windows only for pushes to `main`. It doesn't package the app. GitHub Actions is out of minutes for now, so CI shows red without running anything. Run `pnpm run verify` instead.

## Architecture

- `src/main`: the Electron main process. `Window` owns a `BaseWindow` with one window-sized chrome view underneath, one `WebContentsView` per tab above it, an overlay view on top for the collapsed sidebar when it floats over the page, and another for the find bar (`src/main/FindBar.ts`).
- `src/main/Layout.ts`: the only place that decides where regions go. `Window` places the tab views with it and sends it to the chrome renderer, which draws each region at those rects. Don't hard-code sizes anywhere else.
- `src/shared/ipc.ts`: the one IPC contract. Every channel, its arguments, its result and which chrome view may call it live here. Add a channel here first, then to `CHANNEL_REGIONS` in `src/main/ipc.ts`, and then to the preload.
- `src/preload`: one sandboxed preload per chrome view, typed against the contract. The `.d.ts` files beside them expose those types to the renderers.
- `src/main/EventManager.ts`: registers every IPC handler, and rejects calls from any view or frame other than the one the contract names.
- `src/shared/library.ts`: what the sidebar and pages show, all of it saved locally.
- `src/main/BookmarkStore.ts`: one list of saved sites in a JSON file. There are two of them, `bookmarks.json` and `pinned.json`, and the chrome's `useSavedSites` puts them together for the cluster and the bookmarks bar.
- `src/main/Routines.ts`, `RoutineStore.ts` and `routineSchedule.ts`: the scheduler, its SQLite file and the schedule rules. A run goes through `Chats.runTask`, the same path as a chat with no page, and answers approvals through `chat:decide` under the run's id.
- `src/main/Chats.ts`, `ChatStore.ts` and `agent.ts`: every chat runs through `Chats`, which saves to SQLite and gets replies from a LangChain agent. Keys come from `.env` (see `.env.example`). LangChain loads on the first message, so startup never waits for it. A cheap model from the same provider names each chat once it has a topic, and a title the user chose is never replaced.
- `src/main/browserTools.ts`: what Berry can do in the browser, as plain tool definitions that `agent.ts` hands to LangChain. Each call shows in the chat as a step, saved with the reply. While Berry can see a page, the tools reach every open tab. Otherwise they reach only the tabs that chat opened itself, until the user takes one over by clicking, typing or navigating there. Going to a tab to watch doesn't. Every tab Berry opens stays behind the user, and a call naming no tab stays on the job's own tab, not the one the user is on. A tool with `describe` changes something. Depending on the Ask before acting setting and its `isRisky`, it pauses on an approval card that says exactly what will happen, through LangChain's human-in-the-loop middleware, and does nothing if the page has changed since the user allowed it. `pageScripts.ts` holds what they run in the page, in an isolated world, which also reaches same-origin frames. `pageInput.ts` sends real mouse and keyboard input to the tab's view. A frame from another origin runs its scripts in its own page's world and gets scripted input, its refs look like `f1.e5`, and it always asks in the default mode, because it can answer anything about itself. A step limit in `agent.ts` ends a run with a last call that writes up what it has.
- `src/main/PageActor.ts`, `pageActorScript.ts` and `pageActorArt.ts`: the working mascot drawn on the page (see Over a web page in DESIGN.md). `PageActor`, one per `Tab`, decides what shows and how long to wait, and every call does nothing unless the user is looking at that tab. `browserTools.ts` asks `actorOn(tab)` first and takes its old path with no bird, and after any flight checks that the job wasn't stopped or the tab taken over before acting. `pageActorScript.ts` is what runs in the page, in the tools' isolated world: a closed shadow root in the top layer, no box and no pointer events, a constructed stylesheet and elements made with `createElementNS`, since a strict CSP and Trusted Types refuse anything else, even from there. It only draws. Stop is `tab:stop-work`, in the toolbar, so no page can reach it: don't add a control to the layer. `pageActorArt.ts` is generated from `Mascot.tsx`, `tokens.css` and `tailwind.config.js` by `pnpm run site:build`. `Tab.screenshot` hides the bird for its capture.
- `src/main/MascotStore.ts` and `src/shared/mascots.ts`: the flock, saved to `mascots.json`, with Berry always first and never on file. `mascots.ts` is shared runtime code, so preloads may only `import type` from it. A mascot can only narrow: `createPageTools` takes `limits`, drops tools it wasn't given, and refuses anything off its sites in `run` and in `refuses`, which `agent.ts` checks before asking so a refused call gets no card. Approvals don't read the profile at all. A new tool must be listed in `TOOL_NEEDS` or no mascot gets it. A deleted or missing mascot never falls back to Berry. Its name and instructions go into the prompt through `mascotNote.ts`, after the safety rules, each in a tag saying what it is.
- `src/main/mascotCatalog.ts` and `Gallery.ts`: what the Gallery lists, the bundled starters and what people published. Add takes an entry's id, so main copies what the page last showed, even if its author has changed it since, through `MascotStore.addFromGallery` and `parseMascotDraft`. The copy runs like any mascot and never reads the entry again: `galleryId` only tells the Gallery it's added. `permissionsInWords` in `mascots.ts` is the one source of a mascot's permission wording. Examples on starters, in `starterExamples.ts`, come from real runs only, through the `example-` jobs in `evals/`.
- `src/shared/publishing.ts`: the rules for anything from or to strangers, on top of `parseMascotDraft`. Rows go through `parsePublishedRow` when they're read, whoever wrote them, and invisible characters are taken out so what's reviewed is what the model reads. Publishing sends `publicRow` and nothing else, and main reads the mascot itself, taking only the author, line, category and example from the renderer.
- `src/main/galleryServer.ts`: every call to Supabase, with `fetch` and the publishable key. `serverConfig` refuses any other key, and only an unpackaged app can be pointed at 127.0.0.1, which is how tests use `tests/fakeSupabase.ts`. With `SUPABASE_URL` unset there's no server, and no sign-in or publish control shows.
- `src/main/Account.ts`: email and password, typed in the chrome's own form. The session stays in main, encrypted with `safeStorage`, and renderers only get the state and the email. No tool or mascot can reach any of it, so don't add one.
- `supabase/migrations`: the tables, row-level security, column grants and the `record_add` function, which are the real enforcement. `supabase/gallery.test.ts` runs them on real Postgres in WebAssembly, as the roles Supabase uses. No service key belongs in the repo or the app.
- `site/`: the public page for a mascot at `site/m/?id=`, static, with no build for the host to run. It reads with the publishable key from `site/config.js`, and everything from the server goes in as text.
- `Chats.waiting` and `Window.needsYou`: what the Needs you page shows, every run with an approval, in the library snapshot. It answers through `chat:decide`. `hand_to_user` makes a `handoff` approval: `Chats.handedOver` keeps the tab from every job and every message until the user presses I'm done, which is the only thing that gives it back, and nothing typed goes through us.
- `src/main/Phone.ts`, `phoneReplies.ts`, `TelegramChannel.ts` and `codeEntry.ts`: answering Needs you from the phone. `Phone` decides what to send and what a reply means, through the small `PhoneChannel` interface, and knows nothing about Telegram. `TelegramChannel` is the user's own bot: long polling, pairing, and the token encrypted with `safeStorage`, which never leaves main once saved. `BLUEBERRY_TELEGRAM_API` points it at a fake server, only in an unpackaged app and only at 127.0.0.1. A code goes from the reply through `Chats.enterCode` to `codeEntry.ts`, which types it with `Tab.sendInputWhileHeld`, the only way to use a held tab. No tool can reach any of it and the model never gets the code, so don't add one or pass it through `chat:decide`. `Chats` also takes entered codes out of what goes to the model, in case a page repeats them, along with the query and fragment of a tab's address just after a handoff.
- `src/main/Suggestions.ts` and `suggestionPatterns.ts`: what the birds on the new tab page say, drawn by `BirdsOnFruit.tsx` on the outline of the art blueberry, which also draws the chats, routines and ideas shown when there are no suggestions. Patterns are plain code, found fresh on each new tab, and they write the reason. The cheap model only writes the other words, saved to `suggestions.json`, at most about once an hour. It can't set a card's kind, schedule, sites or tools, and a card only fills in a form or the composer.
- `src/main/HistoryStore.ts`: every visit, in SQLite, with `importVisits` for bringing history in from another browser. `src/main/browserHistory.ts` reads that from Chromium-format browsers: it copies a profile's `History` file to a temp folder, reads only address, title and time from `urls` and `visits`, and always deletes the copy. Renderers name a source by id and never pass a path, and no tool can reach any of it, so don't add one. `BLUEBERRY_BROWSER_DATA` points it at another folder, only in an unpackaged app, and `tests/app.ts` always sets it so tests never look at real browsers. Strawberry and Safari aren't sources: Strawberry's history is another format, and Safari needs Full Disk Access. `src/main/database.ts` opens it and `ChatStore`: a damaged file is moved aside, never deleted, and anything else leaves the file alone and runs from memory for that launch.
- `src/main/Session.ts`: the open tabs and layout, saved to `session.json` soon after each change. A restored `Tab` has no view until it's first needed. Anything that needs an answer from a page goes through `Tab.fromPage`, so a crashed or stuck page gives an error rather than a hang.
- `src/main/SettingsStore.ts`: saved settings in the user data folder. Validate anything new in `sanitizeSettings`.
- `src/main/Downloads.ts`: every download, saved to `downloads.json`. Renderers name a download by id and never pass a path. `sessionHandlers.ts` connects it and `SitePermissions` to the session, once, before anything loads.
- `src/main/SitePermissions.ts`: what sites may use, saved per origin to `site-permissions.json`. Anything it doesn't list is refused. `PermissionPromptView.ts` is the only view that can answer a request: `permissions:decide` accepts no other region, and Berry's tools only reach tabs.
- `src/renderer/chrome`: the one chrome renderer, drawing the sidebar or tab row, toolbar, chat panel, glass, and internal pages such as the new tab page, which open as tabs with no web view. The overlay view loads the same page with `?view=overlay`. Shared code lives in `src/renderer/common`.
- `src/renderer/common/components/Mascot.tsx`: Berry and the flock, behind `<Mascot mood size look>`. Screens use the chrome's `Berry` wrapper, which applies Show Berry and Keep Berry still. Replace the artwork here without touching screens, and add new components to the gallery page (View > Component Gallery).
- `src/renderer/chrome/src/components/Composer.tsx` and `ChatMessage.tsx`: the one composer and message layout, used by the new tab page, the main chat and the chat panel. Change them here so the chats stay alike. `ChatApprovalCard` and `ApprovalCard.tsx` show approvals everywhere but Needs you. `siteNames.ts` only shortens addresses for the sentence on top, so the exact words from `describe` always stay under it in full.
- Web pages run in `Tab` views with no preload and no Node access.

## Traps

- **Blank app, but `pnpm dev` works:** the built renderer pages are at `out/renderer/<name>/index.html`. `src/main` must load that path.
- **Packaged app stuck with no window:** a load error in the main process shows a modal dialog, which can sit behind other windows. Declare every runtime import in `dependencies`, including peer dependencies such as `@langchain/core`. pnpm can resolve an undeclared package in development that packaging leaves out.
- **Electron starts as Node:** some shells, including agent shells, export `ELECTRON_RUN_AS_NODE=1`. Unset it to run Electron by hand. `tests/app.ts` already removes it.
- **`executeJavaScript`:** the code is a script, not a function body, so a top-level `return` is a syntax error.
- **Preloads load nothing but `electron`:** they're sandboxed, so a shared runtime import becomes a chunk the preload can't `require`, and the chrome loses its API. Preloads may only `import type` from other files.
- **Views stack by order:** a tab view covers the chrome beneath it, so CSS in the chrome can't draw over a page.
- **Parked tabs:** a view wholly outside the window gets no size and draws nothing on Windows, so a tab Berry works in behind the user's keeps one corner pixel in the window, under the chrome, which takes any click there. `parkedPage` in `Layout.ts` and `Window.placeTab` do this.
- **Tests run off-screen:** outside CI, `tests/background.cjs` keeps the test app off-screen and out of the foreground, so they don't disturb the Mac. Take screenshots with Playwright, not `screencapture`.
- **Asking about site permissions:** Electron has no "not asked yet" answer, so `Notification.permission` and `navigator.permissions.query` say `denied` until the user allows. The request itself still reaches the prompt.
- **`getUserMedia` in tests:** allowing it can raise the Mac's own permission dialog. Tests only ever block it.
- **Real input isn't checked by Electron:** `sendInputEvent` goes wherever the coordinates are, or nowhere. It doesn't reach a frame from another origin, and pages move after a scroll, so aim after they settle. `aimClick` watches for the press and stops one landing on anything but the named element.
- **Native drags and pickers:** real input on a `draggable` element starts a Mac drag that would catch the user's pointer, and a real click on a dropdown or file field opens a native menu or file picker. Those are scripted.
- **The bird changes when a click happens:** `aimClick` runs again after the flight, so the watch on the press is set where the element is now, and a press on anything else is still stopped. Nothing the bird draws can be hit, so it never needs telling apart. Anything new that waits for it must end through `PageActor`'s waits, or it holds up a job after the bird has gone.
- **Formatting:** existing files aren't Prettier-clean, which is most of the lint warnings. Don't run `pnpm format` over files you aren't otherwise rewriting.
