# Blueberry

An AI browser built with Electron, React and TypeScript. [DESIGN.md](./DESIGN.md) is the source of truth for all UI, so read it before changing anything visible. [README.md](./README.md) says what it does, and [docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md) walks through how it fits together.

## Commands

| Command | What it does |
|---|---|
| `pnpm install` | Install dependencies |
| `pnpm dev` | Run the app with hot reload |
| `pnpm run typecheck` | Typecheck main, preload, tests and renderers |
| `pnpm run lint` | Lint. Warnings are allowed, errors fail CI |
| `pnpm run test` | Run unit tests in `src/` with Vitest |
| `pnpm exec electron-vite build` | Build into `out/` |
| `pnpm run test:e2e` | Run Playwright against `out/`, so build first |
| `pnpm exec electron-builder --dir` | Package an unsigned app into `dist/` |
| `pnpm run eval` | Run Berry on real websites with the real model, which costs money. See `evals/README.md` |
| `pnpm run site:build` | Regenerate what comes from the app: in `site/`, the drawings, the phone page's poses, permission wording and checks on a row, and `src/main/pageActorArt.ts`, the bird drawn on pages. Run it after changing any of them |
| `pnpm run site:deploy` | Deploy `site/` to Netlify, as it is, with `netlify.toml`. Needs `npx netlify login` and a linked site first |
| `pnpm run push:keys` | Print a new VAPID key pair for notifications on the phone page. See `runner/README.md` |
| `pnpm run runner:build` | Bundle the cloud runner into `runner/dist/`. `pnpm run runner:start` runs it. See `runner/README.md` |
| `pnpm run verify` | Typecheck, lint, unit tests, build and end-to-end tests, the same as CI on macOS |

CI runs typecheck, lint, unit tests and build on macOS and Windows. It doesn't run the end-to-end tests, because 15 of them need a real screen and GitHub's runners have none, and it doesn't package the app. The end-to-end tests run on a Mac with `pnpm run verify`, and nothing checks them on Windows yet.

## How we build

- **One branch and one PR per working feature, from the latest `main`.** Don't stack PRs. Each runs in its own worktree.
- **Every PR goes through `self-check`, proof and `file-pr`.** One `review-loop` round only for changes that touch what Berry may do, permissions or secrets.
- **Run `pnpm run verify` before filing.** It runs what CI runs on macOS. Put the result in the PR.
- **The project manager agent merges.** It merges PRs one at a time and reruns `verify` on anything `main` has moved under.
- **The user merges anything that lets Berry do more without asking.** Say so at the top of the PR.
- **Tests stay small:** one end-to-end test of the main flow, plus unit tests only for real logic. If a test fails with no link to the change, rerun it once and move on. Look into it only if the same test keeps failing. Don't write tests for test helpers.
- **Fake models only prove plumbing.** A change to what Berry does also needs a real run with the key in `.env`, on real sites, and the PR says what it cost. Link `.env` from the main checkout into your worktree when you need it. Never print it or commit it.
- **New screens are built from [DESIGN.md](./DESIGN.md), with no mockup step.** Look at them in the running app in both layouts, light and dark, and attach what you saw. A screen DESIGN.md doesn't cover yet gets a section there in the same PR.
- **No dead controls.** Anything visible works, or says why it can't yet. Remove sample data when the real feature arrives.

## Architecture

- `src/main`: the Electron main process. `Window` owns a `BaseWindow` with one window-sized chrome view underneath, one `WebContentsView` per tab above it, an overlay view on top for the collapsed sidebar when it floats over the page, and another for the find bar (`src/main/FindBar.ts`).
- `src/main/Layout.ts`: the only place that decides where regions go. `Window` places the tab views with it and sends it to the chrome renderer, which draws each region at those rects. Don't hard-code sizes anywhere else.
- `src/shared/ipc.ts`: the one IPC contract. Every channel, its arguments, its result and which chrome view may call it live here. Add a channel here first, then to `CHANNEL_REGIONS` in `src/main/ipc.ts`, and then to the preload.
- `src/preload`: one sandboxed preload, `chrome.ts`, shared by every chrome view and typed against the contract. `chrome.d.ts` beside it exposes those types to the renderers.
- `src/main/EventManager.ts`: registers every IPC handler, and rejects calls from any view or frame other than the one the contract names.
- `src/shared/library.ts`: what the sidebar and pages show, all of it saved locally.
- `src/main/BookmarkStore.ts`: one list of saved sites in a JSON file. There are two of them, `bookmarks.json` and `pinned.json`, and the chrome's `useSavedSites` puts them together for the cluster and the bookmarks bar.
- `src/main/Routines.ts`, `RoutineStore.ts` and `routineSchedule.ts`: the scheduler, its SQLite file and the schedule rules. A run goes through `Chats.runTask`, the same path as a chat with no page, and answers approvals through `chat:decide` under the run's id.
- `src/main/Chats.ts`, `ChatStore.ts` and `agent.ts`: every chat runs through `Chats`, which saves to SQLite and gets replies from a LangChain agent. Keys come from `.env` (see `.env.example`). LangChain loads on the first message, so startup never waits for it. A cheap model from the same provider names each chat once it has a topic, and a title the user chose is never replaced.
- `src/main/browserTools.ts`: what Berry can do in the browser, as plain tool definitions that `agent.ts` hands to LangChain. Each call shows in the chat as a step, saved with the reply. While Berry can see a page, the tools reach every open tab. Otherwise they reach only the tabs that chat opened itself, until the user takes one over by clicking, typing or navigating there. Going to a tab to watch doesn't. Every tab Berry opens stays behind the user, and a call naming no tab stays on the job's own tab, not the one the user is on. While a chat's reply runs, `Chats.jobChatOf` puts its tabs under the chat in the sidebar (`TabInfo.jobChatId`). When it ends, `Chats.closeJobTabs` closes them, except one the user took over, the last one when the reply names its site (`replyPointsTo` in `jobTabs.ts`), and any held or in use, and saves their addresses on the reply as `pages` through `addressToKeep`. Routine runs close theirs in `Routines` as before. A tool with `describe` changes something. Depending on the Ask before acting setting and its `isRisky`, it pauses on an approval card that says exactly what will happen, through LangChain's human-in-the-loop middleware, and does nothing if the page has changed since the user allowed it. In the default mode `go_to` and `open_tab` ask unless the address is plainly safe: one the user gave, a short search on a listed search page, or a plain address on a site the job has reason to be on, because the user named it, the bird is limited to it, or this reply or an earlier one in the chat was on it. A reason to be on a site never covers data: a query, a long path, an escape, an `@` or `=`, six digits in a row, a long word or one like hex or base64 in the path or host, or a new subdomain of a site it has only been to. A name or password in an address always asks, on any site. A link on the page changes none of this, since a page can plant links. With `FIRECRAWL_API_KEY` set, `web_search` asks Firecrawl (`webSearch.ts`) for a few results as title, address and snippet, labelled untrusted, and asks first unless the query passes `plainSearch`, the same check as data in an address. The key stays in main, and a bird limited to sites doesn't get the tool. `pageScripts.ts` holds what they run in the page, in an isolated world, which also reaches same-origin frames. `pageInput.ts` sends real mouse and keyboard input to the tab's view. A frame from another origin runs its scripts in its own page's world and gets scripted input, its refs look like `f1.e5`, and it always asks in the default mode, because it can answer anything about itself. A step limit in `agent.ts` ends a run with a last call that writes up what it has.
- `src/main/pageTarget.ts`: the interface the tools work through, `PageTarget`, types only. `Tab` is one, `CdpTab` the other, and `createPageTools` is generic over which. Add anything new a tool needs here first and to both. `actor` is null where nobody sees a bird, and the tool layer, `pageScripts.ts` and `pageInput.ts` must not import Electron at runtime, so a runner without a window can use them.
- `src/main/CdpTab.ts`, `cloudBrowser.ts`, `browserbase.ts` and `localChrome.ts`: a browser reached over CDP, in plain Node through `playwright-core`, loaded on first use. `CdpTab` runs scripts in one isolated world per document, sends real input with `Input.dispatch*`, and holds a navigation limit with the `Fetch` domain only while one is on. `CloudSessions` keeps one session and lets one job claim it at a time. End releases it at the provider first, from the saved session id alone, so a lost or failed connection still stops the cost, and a release that isn't confirmed stays in Settings > Cloud with Try again. A popup is never a page of its own: its requests are refused and its address loads only in the tab that opened it. `localChrome.ts` is the stand-in for tests: a headless Chrome with a throwaway profile, or one already on 127.0.0.1.
- `src/main/CloudTabs.ts`: Settings > Cloud and the cloud tabs in the window, internal pages of kind `cloud` drawn by `CloudPage.tsx`. The key and project id are kept with `safeStorage` in `cloud.json` and never sent to a renderer. The live view address, checked to be Browserbase's, and the local browser's pictures go to the chrome only, never to a tool, a chat or the disk. `Chats.send` with `cloud: true` runs a chat there, and its later messages follow, in memory only. A cloud job reaches only the pages it opened there, never the window's tabs. `BLUEBERRY_CLOUD_LOCAL` (`1`, or an address on 127.0.0.1) and `BLUEBERRY_CLOUD_CHROME` only work in an unpackaged app. Cloud tabs aren't saved with the session.
- `src/main/cloudLogins.ts` and `cloudLoginAccess.ts`: Settings > Cloud > Signed in to. `cloudLogins.ts` is plain Node: `cookiesForSite` and `cookieDomainPattern` decide which cookies are a site's (the site, its subdomains, and domain cookies its parents set for it), and `CloudLogins` asks first, then reads, writes them in with `context.addCookies` through `CloudSessions.withContext`, and keeps `cloud-logins.json` with names, dates and a status only. `cloudLoginAccess.ts` is the Electron part: Touch ID or a confirm dialog, then one cookie lookup for the site and one for each parent domain, never one for everything, with anything not the site's dropped before it leaves. Browserbase saves them into the Context when the session ends, because it's made with `persist: true`. Only the `cloud:*-login*` channels from the chrome start any of it: no tool, mascot, MCP app or phone reaches it, and no cookie value goes to a renderer, a log or the disk, so don't add a route or print an error from it. `BLUEBERRY_CLOUD_CONFIRM` (`allow` or `deny`) answers the confirm, only in an unpackaged app. A check tab is opened with `CloudSessions.openForUser`, belongs to no job and is the user's from the start. `hand_to_user` on a cloud page goes through `Chats.handOverInCloud`, with the same `handedOver` map as a local tab: the user takes the cloud tab over to type in the live view, and I'm done gives it back through `ChatCloud.giveBack`. A code can't come from the phone there yet.
- `runner/`, `src/main/RunnerJobs.ts` and `cloudJobs.ts`: the cloud runner, a plain Node service for Railway that runs jobs while the Mac is off. It runs the app's own `Chats.runTask` with `cloud: true`, so the agent, tools, mascot limits, approvals and step limit are the chat's, in a Browserbase session on the Context id the job carries, ended with the job. Don't give it an agent of its own. `Chats` takes a `ChatStoreLike`, so the runner passes one with no chats, and the runner never imports Electron. It signs in to Supabase as a user of its own, with email and password and the publishable key only, through `runnerSession` in `runner/src/db.ts`, never a secret key or JWT secret. It counts as a runner once a row in `cloud_runner_links` links it: the owner offers it from Settings > Cloud > With your Mac off by the runner's email, and the runner accepts when it starts, naming `BLUEBERRY_RUNNER_OWNER` back, so nobody can point their jobs at someone else's runner, or make someone's own account a runner. One runner per owner and one owner per runner. `start_cloud_job` needs an accepted runner, and it and accepting a link take the same per-account lock, `lock_cloud_account`, before they check anything, so an account can't end up both a runner and an owner of jobs. The app looks at the link again every few minutes and whenever the new tab page opens. Owner and runner are both `authenticated`, so no column grant can tell them apart: nobody writes `cloud_jobs` or `cloud_approvals` directly, and every write is a security definer function that checks who's calling with `cloud_runner_for()`. It writes an approval as a row, waits for the decision, and stops after 30 minutes with none. It can read an approval only while its cloud job is unfinished, so past questions and answers stay the owner's. Only `decide_cloud_approval` writes a decision, and it refuses any linked runner, so nothing on the runner can answer, and `Chats.decide` refuses a runner chat's approval from the phone or an app. `cloudJobs.ts` is pure: what goes into a row and the checks on what comes out, where `mascotFromSnapshot` only lets a mascot through `parseMascotDraft`, Berry's id is unlimited only with no limits in the row, and a job never asks less than the default, so "Never ask" runs as risky. A row is written with the user's session, so a stolen session could queue any bird, but it could answer the approvals too: the session is the line. `runner/src/quietConsole.ts` keeps only a log line's first words on the runner, since the shared code logs errors whole. In the app, `RunnerJobs` is a `ChatRunner` inside `Chats`, available only once a linked runner has accepted: a runner chat is saved here like any other, and its steps and approval are polled from `my_cloud_jobs` as the signed-in user. A chat is one conversation, `conversation_id` on every job of it, and a follow-up is a new job there carrying the messages before it as `history`, built the same way on both sides by `followUpHistory`, `asHistoryMessage` and `fitHistory` in `src/shared/phone.ts`: the user's words and the bird's replies with notes of their steps, nothing more. `start_cloud_job` refuses one while another job of the conversation is going, as 409, and a unique index holds it too. It also refuses one whose `p_after_job` isn't the conversation's newest job, the one its history was built on, so a follow-up can't skip an exchange sent from the other side: the app (`RunnerJobs.catchUp`) and the phone then read the conversation again, build the history anew and send once more. In the app a runner message waits in `Chats.runnerPending` until the runner has it, so what's brought in first is saved before it. `RunnerJobs.discover` looks every 10 seconds for conversations it didn't send, or that went on elsewhere, and makes or extends the runner chat through `Chats.adoptRunnerChat` and `runnerFollowedUp`. Deleting a chat deletes its whole conversation with `forget_cloud_conversation`, and keeps its id so it never comes back. Each one belongs to the account that sent it: signed out or as someone else, nothing of it shows or can be answered, and it waits rather than ending. The live view address goes through `cloud:runner-view` to the chrome only, and only if it's Browserbase's. The runner logs job ids and outcomes and nothing else, so don't log a prompt, page, cookie or code there. With VAPID keys set, `runner/src/push.ts` sends a Web Push when a job asks and when it ends other than by the user's own Stop. The payload is only `{ kind }`, "needs-you" or "finished", and goes only to a browser's own push service, so don't add a word of the job to it. A routine with `inCloud` runs there instead of here on its schedule, and from then on the server owns when it's due: the Mac's tick never advances it. `Routines.cloudRows` makes its row, with its bird narrowed by its sites through `mascotSnapshot`, and `RunnerJobs.routinesChanged` keeps `cloud_routines` in step through `sync_cloud_routine`, which takes the schedule, the definition and whether it's paused, and uses the first run it's sent only for a new routine, a changed schedule or a resume. Deletes reconcile against the server's own keys from `my_cloud_routine_keys`, so one that failed is forgotten on a later round or launch. `runner/src/routines.ts` asks `runner_due_routines`, which gives the runner only a routine's id, schedule, zone and due time, works out the next time with the app's own `nextRun` in that zone, and `runner_start_routine` makes the owner's job and moves the routine on in one step. Each job carries its occurrence, unique per routine, so one occurrence starts at most one job. That job is then claimed and checked like any other, and shows in the app as a runner chat through `discover`. A Berry snapshot with sites is Berry on only those, which only narrows.
- `runner/src/relay.ts`, `relayAuth.ts` and `relayTools.ts`: the relay, a public MCP endpoint at `/mcp` on the runner for ChatGPT and Claude, on only with `RELAY_PUBLIC_URL` and `RELAY_SECRET`. It never keeps the owner's session. `relayAuth.ts` is the OAuth server behind the SDK's `mcpAuthRouter`: clients are signed, not stored, and may only redirect to ChatGPT, Claude or loopback. The sign-in page refuses any account but `BLUEBERRY_RUNNER_OWNER` before sending anything or counting a try. It uses the owner's session once, for `create_relay_grant`, then signs it out, and keeps only the grant's secret, sealed with `RELAY_SECRET` in `RELAY_STATE_FILE` if set. A reused refresh token ends the connection, and connections end after 30 days idle or 90 days. Every other call is the runner's own session through the `relay_*` functions in `20261106000000_cloud_relay.sql`, which check the secret's hash, that the grant is the caller's and its link still accepted, and then act as the owner for that one thing. A grant only sees jobs it started (`cloud_relay_jobs`). Unlinking, re-offering or replacing the runner revokes its grants by trigger, and `revoke_relay_grants` is Settings' Disconnect. There's no relay function that decides anything, so don't add one, or any tool that answers: a question or approval waits for the user in the app or on the phone. `relayTools.ts` is the tool layer over a small `RelayHost`: `start_job` sends the phone's snapshot with sites only narrowed by `narrowSites`, and steps and replies go out labelled as untrusted. The runner writes the address to `cloud_runner_links.relay_url` through `runner_set_relay_url`, and the app shows it in Settings > Cloud through `my_cloud_runner`, only an https one.
- `src/main/MacJobs.ts` and `20261107000000_relay_on_mac.sql`: relay jobs on the user's Mac. `start_job`'s `where` (`auto`, `mac` or `cloud`) goes to `relay_start_job`, which sends `auto` to the Mac only if `mac_available`: the switch `relayOnMac` (Settings > Cloud, off by default) is on in `cloud_mac_presence` and the app was seen in the last minute. `mac` with no Mac gives null, and the relay says Blueberry isn't open there. A Mac job is a `cloud_jobs` row with `target` 'mac', and every runner function and the runner's read policy keep to 'cloud', so the runner never sees one. While the switch is on, signed in with an accepted runner, `MacJobs` reports presence every 30 seconds, claims one at a time through `mac_claim_job` as the owner, which gives nothing with the switch off on the server, and runs it through `Chats.send` with no page and `from` "ChatGPT or Claude", exactly as an MCP job. The row's bird goes through `mascotFromSnapshot`, as on the runner, and must be in the local flock by id, never falling back to Berry. Its `sites`, `tools` and the row's ask level (`askAtLeast`) only narrow the local bird and the Ask before acting setting in `Chats.send`, and `unlimited` in `Chats` is Berry only with every tool and no sites. The job is the one reply it started: `Chats.send`'s `onEnd` says how that reply ended, so a follow-up the user types in the chat afterwards never reaches the relay. Steps, status and the reply go back through `mac_update_job`, cleaned with `withoutCodes`, and its answer says whether the relay asked to stop. Approvals stay on the Mac and only `waiting` reaches the row. Turning the switch off stops the job here at once, then tells the server, which fails what's queued for the Mac, and a claim that comes back after that is failed rather than started. `expire_mac_jobs` ends a Mac job whose app went quiet for 2 minutes, or one nobody took in 5, from `mac_claim_job`, `relay_start_job`, `relay_jobs` and the runner's `runner_claim_job`, so a Mac that's off never holds up the cloud's limit and no job runs twice. `discover` and the phone page read only `target=eq.cloud`, so a Mac job never comes back as a runner chat.
- `site/app/`: the phone page, the user's runner jobs from anywhere, grouped into conversations by `conversationsOf`, with no build. `api.js` is the only way to Supabase, with the publishable key and the user's own session in `localStorage`. It reads `cloud_jobs` and `cloud_flock` as that user, and a follow-up reads the last job's `history` to build the next, as the same bird if it's still in the flock. It writes only through `start_cloud_job`, `decide_cloud_approval`, `stop_cloud_job` and the push subscription functions. Everything from the server goes in as text. The live view is a Browserbase frame, locked unless a handoff has been taken over on this phone, and kept in place across polls, because moving an iframe reloads it. A sign-in or a code is typed into that frame and goes straight to the site: there's no field for one on the page, and a question's answer shaped like a code (`plausibleCode`) isn't sent. `sw.js` shows a push as "Berry needs you" or "Berry finished" and nothing else. Words on the page say "in the cloud", never "runner". `RunnerJobs.flockChanged` shares the flock through `sync_cloud_flock`, only while signed in with an accepted runner, and only name, look, instructions and limits through `flockRows` in `src/shared/phone.ts`, never memory. The phone reads it back through `flockFromRows`, which puts it through `parseMascotDraft`, and sends the same snapshot as the app, which `mascotFromSnapshot` checks on the runner. A job from the phone takes the Context id from the user's last job, since only the Mac knows it, and the app shows it as a runner chat. Settings on the phone holds appearance, kept in `localStorage` by `site/theme.js`, notifications and the account.
- `src/main/PageActor.ts`, `pageActorScript.ts` and `pageActorArt.ts`: the working mascot drawn on the page (see Over a web page in DESIGN.md). `PageActor`, one per `Tab`, decides what shows and how long to wait, and every call does nothing unless the user can see that tab, directly or as a picture in the working view. `browserTools.ts` asks `actorOn(tab)` first and takes its old path with no bird, and after any flight checks that the job wasn't stopped or the tab taken over before acting. `pageActorScript.ts` is what runs in the page, in the tools' isolated world: a closed shadow root in the top layer, no box and no pointer events, a constructed stylesheet and elements made with `createElementNS`, since a strict CSP and Trusted Types refuse anything else, even from there. It only draws. Stop is `tab:stop-work`, in the toolbar, so no page can reach it: don't add a control to the layer. `pageActorArt.ts` is generated from `Mascot.tsx`, `tokens.css` and `tailwind.config.js` by `pnpm run site:build`. `Tab.screenshot` hides the bird for its capture.
- `src/main/WorkViews.ts`: the working view beside the main chat. It decides what's captured and how often, and sends words as `work:updated` and pictures as `work:frame`, to the chrome renderer and nowhere else. `Chats.work` says which tabs a job has used and whether each may be pictured. A tab with a picture on screen counts as watched through `Tab.setPictureScale`, so `PageActor` draws there at its usual pace, larger because the picture is small. Parked tabs render and animate normally. `Tab.picture` is separate from `Tab.screenshot`: it keeps the bird in, checks again after the capture, and its result goes to nothing but `WorkViews`. Don't add a route from it to a tool, a chat or the disk. `ChatPage` draws `WorkingView.tsx`, so `Layout.ts` isn't involved. A cloud job's pages are never captured here: the card shows the cloud tab's own live view, locked, or the local test browser's pictures, through `useCloudView` in `cloudView.ts`, so only the big window has one.
- `src/main/Recordings.ts`, `recorderScript.ts` and `recordingTrail.ts`: Show Berry how. `recorderScript.ts` runs in its own isolated world (`RECORDER_WORLD`), not the tools', and only ever on the tab in front. `Tab.listenInPage` is a long poll: the page answers with what the user did as soon as they do it, which reaches main before a click's navigation, and a new document simply never answers. Secret fields are decided before `.value` is read, so their values never exist outside the page, and `isTrusted` is checked on every event. The clipboard is never read: a copy is the page's selection, or the field's selected range, and a paste is only noted, its text read from the field when the user finishes with it. `recordingTrail.ts` is pure: the notes, how addresses lose their query, and what the model may change. The trail lives only in `Recordings`, and `recording:draft` is the only thing that sends it, as tagged data to the cheap model. Sites come from the trail, in code, and the result only fills in `RoutineForm`. A routine's `sites` go through `narrowSites` and the tool layer's `limits`, so they can only take away. A run never asks about a recording, and no tool or mascot can reach one, so don't add one.
- `src/main/MascotStore.ts` and `src/shared/mascots.ts`: the flock, saved to `mascots.json`, with Berry always first and never on file. `mascots.ts` is shared runtime code, so preloads may only `import type` from it. A mascot can only narrow: `createPageTools` takes `limits`, drops tools it wasn't given, and refuses anything off its sites in `run` and in `refuses`, which `agent.ts` checks before asking so a refused call gets no card. With sites, `screenshot` and the page sent with a message go without a picture while the browser's frame tree has a frame from another site, on screen or not, checked before and after the capture (`showsFrameOffLimits`), and the text says why. Approvals don't read the profile at all. A new tool must be listed in `TOOL_NEEDS` or no mascot gets it. A deleted or missing mascot never falls back to Berry. `worksInCloud` lives on the profile only, outside `MascotDraft`, so publishing, the phone's flock and Gallery copies never carry it, and all it does is turn on Do this in the cloud in the new tab composer. Its name and instructions go into the prompt through `mascotNote.ts`, after the safety rules, each in a tag saying what it is.
- `src/main/MemoryStore.ts`, `mascotMemory.ts` and `src/shared/memory.ts`: what a bird remembers (see What a bird remembers in DESIGN.md), in `memory.json`, apart from the mascot so nothing that copies or publishes one can take it along. `Chats` proposes after a finished job through `offerToRemember`, and only if `statesAHabit` finds words in what was just typed that go beyond the job, because a bird should rarely have anything to say, and the model only ever gets what the user typed, the questions they answered and the site names, never a page, a step or the reply, so don't add any of those to `proposalData`. An offer lives in memory only and becomes a fact only through `memory:decide`, by id. `factProblem` is the one check on anything stored, and `parseProposals` adds to it for what the model wrote. `relevantFacts` decides what goes into a job, and `memoryNote` in `mascotNote.ts` is how it goes in. Replies and runs keep only fact ids, so forgetting takes it off them too. No tool or mascot can reach any of it, and limits and approvals don't read it, so don't add a route.
- `src/main/mascotCatalog.ts` and `Gallery.ts`: what the Gallery lists, the bundled starters and what people published. Everything main sends the page carries a `version`, a hash of what a copy is made from, and `Gallery` keeps each version it sent. Add takes the entry's id and the version the review showed, so main copies exactly that one, even if its author has changed it since or another fetch of the same id came back in between, and refuses a version it never sent. It goes through `MascotStore.addFromGallery` and `parseMascotDraft`. The copy runs like any mascot and never reads the entry again: `galleryId` only tells the Gallery it's added. `permissionsInWords` in `mascots.ts` is the one source of a mascot's permission wording. Examples on starters, in `starterExamples.ts`, come from real runs only, through the `example-` jobs in `evals/`.
- `src/main/mascotLink.ts`: `blueberry://` links, which any website can hand to the system, so treat one as a stranger's. `index.ts` registers the scheme, with `protocols` in `electron-builder.yml` for a packaged app, takes the single-instance lock, and reads links from `open-url` on a Mac and from a second launch's arguments, or the first launch's, elsewhere. Only `blueberry://mascot/<uuid>` is read, by `mascotFromLink`, and anything else does nothing. `Window.openMascotLink` brings the window forward and opens the Gallery tab with the id as its param, plus `gallery:linked` for a Gallery already showing it, and the page asks the server for that one entry through `Gallery.linked` and opens its review. Every link counts as a new ask, even the same one twice. `linkThrottle` drops the same id again within a few seconds, brings the window forward at most every two, and after three links in ten seconds, whatever the ids, ignores every link for thirty, so a page can't keep taking the front. A link never adds, runs or changes anything, so don't read anything more from one. An unpackaged app registers Electron itself, with the app's folder as its argument. Tests never register: `tests/fakeProtocol.cjs` only writes it down, and a test delivers a link by emitting `open-url` or `second-instance`.
- `src/shared/publishing.ts`: the rules for anything from or to strangers, on top of `parseMascotDraft`. Rows go through `parsePublishedRow` when they're read, whoever wrote them, and invisible characters are taken out so what's reviewed is what the model reads. Publishing sends `publicRow` and nothing else, and main reads the mascot itself, taking only the author, line, category and example from the renderer.
- `src/main/galleryServer.ts`: every call to Supabase, with `fetch` and the publishable key. `serverConfig` refuses any other key, and only an unpackaged app can be pointed at 127.0.0.1, which is how tests use `tests/fakeSupabase.ts`. With `SUPABASE_URL` unset there's no server, and no sign-in or publish control shows.
- `src/main/Account.ts`: email and password, typed in the chrome's own form. The session stays in main, encrypted with `safeStorage`, and renderers only get the state and the email. No tool or mascot can reach any of it, so don't add one.
- `supabase/migrations`: the tables, row-level security, column grants and the `record_add` function, which are the real enforcement, and the cloud runner's jobs, approvals and runner links, and the phone page's shared flock and push subscriptions, each the owner's only, with the runner reading just its owner's push addresses through `runner_push_subscriptions`. `supabase/gallery.test.ts`, `cloudJobs.test.ts` and `phone.test.ts` run them on real Postgres in WebAssembly, as the roles Supabase uses. No service key belongs in the repo or the app.
- `site/`: the public page for a mascot at `site/m/?id=` and the phone page at `site/app/`, static, with no build for the host to run, deployed to Netlify with `netlify.toml`. It reads with the publishable key from `site/config.js`, and everything from the server goes in as text.
- `Chats.waiting` and `Window.needsYou`: what the Needs you page shows, every run with an approval, in the library snapshot. It answers through `chat:decide`. `hand_to_user` makes a `handoff` approval: `Chats.handedOver` keeps the tab from every job and every message until the user presses I'm done, which is the only thing that gives it back, and nothing typed goes through us.
- `src/main/Phone.ts`, `phoneReplies.ts`, `TelegramChannel.ts` and `codeEntry.ts`: answering Needs you from the phone. `Phone` decides what to send and what a reply means, through the small `PhoneChannel` interface, and knows nothing about Telegram. `TelegramChannel` is the user's own bot: long polling, pairing, and the token encrypted with `safeStorage`, which never leaves main once saved. `BLUEBERRY_TELEGRAM_API` points it at a fake server, only in an unpackaged app and only at 127.0.0.1. A code goes from the reply through `Chats.enterCode` to `codeEntry.ts`, which types it with `Tab.sendInputWhileHeld`, the only way to use a held tab. No tool can reach any of it and the model never gets the code, so don't add one or pass it through `chat:decide`. `Chats` also takes entered codes out of what goes to the model, in case a page repeats them, along with the query and fragment of a tab's address just after a handoff.
- `src/main/Suggestions.ts`, `suggestionDigest.ts`, `suggestionProposals.ts` and `suggestionPatterns.ts`: what the birds on the new tab page say, drawn by `BirdsOnFruit.tsx` on the outline of the art blueberry, which also draws the chats, routines and ideas shown when there are no suggestions. `suggestionDigest.ts` is pure: it builds what the cheap model reads, sessions, search queries, chats, routines, the flock and feedback, each with a short id such as `s3` or `q2`, and `searchQuery` is the one place a search engine's address counts, only for its query. The model proposes jobs citing those ids, at most about once an hour, and `verifyProposals` in `suggestionProposals.ts` checks every one: the ids exist, sites only come from the evidence, numbers only from what it cites, a schedule only from when the user really looked, and nothing like a dismissed card or something already set up. What passes is saved to `suggestions.json` with its sources, and goes when they leave the history. Without a model or anything valid, `suggestionPatterns.ts`'s old rules find what's repeated and `fallbackWords` words it in code. Dismissed and used cards are kept as feedback through `suggestions:dismiss` and `suggestions:used`. A card only fills in a form or the composer. `evals/suggestionsCheck.ts` runs the real model once on a made-up profile.
- `src/main/DesktopBerry.ts`, `desktopBerryState.ts` and `src/renderer/chrome/src/DesktopApp.tsx`: the bird behind the edge of the screen (see On your desktop in DESIGN.md), off by default. Two `panel` windows, the transparent `desktop` one for the bird and the `composer` one for the prompt box, made when it's turned on and destroyed when it's off or the main window closes. All it can do is `Chats.send` with no page and open Blueberry, so it adds nothing a chat can't do and has no approvals of its own. `desktopBerryState.ts` is pure: who it shows and what it says. Main decides what a press opens, so the view never names a chat or approval. Placement is in `Layout.ts`. The bird's window keeps one size wherever it stands, its movement is transforms in the view, and it only covers the work area during a flight or a drag. Clicks pass through unless a 50ms check of the pointer finds it over what's showing. No tool can reach any of this, and it must never read the screen, the clipboard or another app, so don't add any of that.
- `src/main/McpConnector.ts`, `mcpTools.ts` and `mcpPages.ts`: Claude Code, Claude Desktop and other apps on this computer using Blueberry over MCP, off by default (Settings > Claude). `McpConnector` is a stateless Streamable HTTP server on 127.0.0.1 only, refusing any other `Host` and any request without the token, which is kept with `safeStorage` and only leaves main when Copy puts a snippet on the clipboard. It also writes `mcp-bridge.cjs` to the user data folder, for apps that only start stdio servers, run by Blueberry's own binary as Node. The activity log is memory only. `mcpTools.ts` is the tool layer over a small `McpHost`: a job is `Chats.send` with no page and a `from`, or a routine's `runNow`, so every limit and approval applies as in a chat. `sites` only narrows. An app answers questions through `chat:decide` and never an approval or a handoff, and nothing shaped like a code. It only reaches chats an app started. Everything from a page is labelled as untrusted, and `read_page` goes through Berry's own tool in `mcpPages.ts`, only on a tab that's open already, since opening an address can send data and that's a job's, with its approvals. It reads memory facts but can't change them, and an app's words are never offered for remembering or counted by Suggestions. Account, phone, Telegram, recordings, cookies and passwords stay out of reach, so don't add a route.
- `src/main/HistoryStore.ts`: every visit, in SQLite, with `importVisits` for bringing history in from another browser. `src/main/browserHistory.ts` reads that from Chromium-format browsers: it copies a profile's `History` file to a temp folder, reads only address, title and time from `urls` and `visits`, and always deletes the copy. Renderers name a source by id and never pass a path, and no tool can reach any of it, so don't add one. `BLUEBERRY_BROWSER_DATA` points it at another folder, only in an unpackaged app, and `tests/app.ts` always sets it so tests never look at real browsers. Safari isn't a source, because it needs Full Disk Access. `src/main/database.ts` opens it and `ChatStore`: a damaged file is moved aside, never deleted, and anything else leaves the file alone and runs from memory for that launch.
- `src/main/Session.ts`: the open tabs and layout, saved to `session.json` soon after each change. A restored `Tab` has no view until it's first needed. Anything that needs an answer from a page goes through `Tab.fromPage`, so a crashed or stuck page gives an error rather than a hang.
- `src/main/SettingsStore.ts`: saved settings in the user data folder. Validate anything new in `sanitizeSettings`.
- `src/main/Downloads.ts`: every download, saved to `downloads.json`. Renderers name a download by id and never pass a path. `sessionHandlers.ts` connects it and `SitePermissions` to the session, once, before anything loads.
- `src/main/SitePermissions.ts`: what sites may use, saved per origin to `site-permissions.json`. Anything it doesn't list is refused. `PermissionPromptView.ts` is the only view that can answer a request: `permissions:decide` accepts no other region, and Berry's tools only reach tabs.
- `src/renderer/chrome`: the one chrome renderer, drawing the sidebar or tab row, toolbar, chat panel, glass, and internal pages such as the new tab page, which open as tabs with no web view. The overlay view loads the same page with `?view=overlay`. Shared code lives in `src/renderer/common`.
- `src/renderer/common/components/Mascot.tsx`: Berry and the flock, behind `<Mascot mood size look>`. Screens use the chrome's `Berry` wrapper, which applies Show Berry and Keep Berry still. Replace the artwork here without touching screens, and add new components to the gallery page (View > Component Gallery).
- `src/renderer/chrome/src/components/Composer.tsx` and `ChatMessage.tsx`: the one composer and message layout, used by the new tab page, the main chat and the chat panel. Change them here so the chats stay alike. `ChatApprovalCard` and `ApprovalCard.tsx` show approvals everywhere but Needs you. `siteNames.ts` only shortens addresses for the sentence on top, so the exact words from `describe` always stay under it in full.

## Traps

- **A window's `hide` event and `isVisible` on a Mac:** Electron fires `hide` and `show` from the occlusion state, so `hide` also means "covered by another window", `isVisible()` is false for a covered window, and neither fires or changes for a window off-screen, as in tests. Don't use them to tell that the user hid it. `Window.hideBlueberry` calls `DesktopBerry.mainWindowGone` itself.
- **`app.hide()` takes every window:** showing any window afterwards brings the whole app back. That's why Hide Blueberry hides only the main window while the bird is out.
- **The desktop windows' focus:** a `panel` takes the keyboard without activating Blueberry, and hiding it gives the keyboard back, which is the composer's whole job. The bird's window is `focusable: false` and never has the keyboard. Tests can't see any of this, because `tests/background.cjs` makes `focus` do nothing.
- **Moving the bird's window makes it judder:** resizing or moving a native window frame by frame isn't synced to the display, and a flight timed from main stops when main does, as it does for half a second when the first message loads LangChain. Anything that moves goes in the view as a transform, and nothing about a mood or a line may change the window's size.
- **Glass on the desktop:** `backdrop-filter` can't see past its own window, and native material fills the whole window with the window's own corners, so it can't be cut to a CSS radius. That's why the composer has a window of its own. None of it shows in a test's screenshot, which only has the web contents.
- **Global shortcuts in tests:** `tests/fakeShortcut.cjs` replaces `globalShortcut`, so a test never takes a key from the person at the computer. Press one through `globalThis.fakeShortcuts`.

- **Cookie domains don't match the way they look:** Playwright's `clearCookies({ domain })` with a string only matches that exact domain, and a domain cookie's is `.example.com`, so a string misses most of a site. Pass `cookieDomainPattern`. Electron can give a host-only cookie's domain with a dot in front too, so go by `hostOnly`, not the dot.

- **Asking the recorder again starts it:** `nextNotes` installs the watching if it isn't there, so nothing may call it after `finishWatching`. `Watched.ended` stops `Recordings.listen`, and `finish` tells whoever's waiting that it's over rather than waking them with notes.

- **Blank app, but `pnpm dev` works:** the built renderer pages are at `out/renderer/<name>/index.html`. `src/main` must load that path.
- **Packaged app stuck with no window:** a load error in the main process shows a modal dialog, which can sit behind other windows. Declare every runtime import in `dependencies`, including peer dependencies such as `@langchain/core`. pnpm can resolve an undeclared package in development that packaging leaves out.
- **Electron starts as Node:** some shells, including agent shells, export `ELECTRON_RUN_AS_NODE=1`. Unset it to run Electron by hand. `tests/app.ts` already removes it.
- **`executeJavaScript`:** the code is a script, not a function body, so a top-level `return` is a syntax error.
- **Preloads load nothing but `electron`:** they're sandboxed, so a shared runtime import becomes a chunk the preload can't `require`, and the chrome loses its API. Preloads may only `import type` from other files.
- **Views stack by order:** a tab view covers the chrome beneath it, so CSS in the chrome can't draw over a page.
- **Parked tabs:** a view wholly outside the window gets no size and draws nothing on Windows, so a tab Berry works in behind the user's keeps one corner pixel in the window, under the chrome, which takes any click there. `parkedPage` in `Layout.ts` and `Window.placeTab` do this.
- **Tests run off-screen:** outside CI, `tests/background.cjs` keeps the test app off-screen and out of the foreground, so they don't disturb the Mac. Take screenshots with Playwright, not `screencapture`.
- **Asking about site permissions:** Electron has no "not asked yet" answer, so `Notification.permission` and `navigator.permissions.query` say `denied` until the user allows. The request itself still reaches the prompt.
- **`getUserMedia` in tests:** allowing it can raise the Mac's own permission dialog. Tests only ever block it.
- **Real input isn't checked by Electron:** `sendInputEvent` goes wherever the coordinates are, or nowhere. It doesn't reach a frame from another origin, and pages move after a scroll, so aim after they settle. `aimClick` watches for the press and stops one landing on anything but the named element.
- **Native drags and pickers:** real input on a `draggable` element starts a Mac drag that would catch the user's pointer, and a real click on a dropdown or file field opens a native menu or file picker. Those are scripted.
- **The bird changes when a click happens:** `aimClick` runs again after the flight, so the watch on the press is set where the element is now, and a press on anything else is still stopped. Nothing the bird draws can be hit, so it never needs telling apart. Anything new that waits for it must end through `PageActor`'s waits, or it holds up a job after the bird has gone.
- **Formatting:** existing files aren't Prettier-clean, which is most of the lint warnings. Don't run `pnpm format` over files you aren't otherwise rewriting.
